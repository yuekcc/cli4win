同一个 bash_prompt，三种语言：C3 / Odin / Zig 性能实测

聚焦「进程启动」开销 · Windows 11 · i7-12650H · 2026-10-12 · 仓库 cli4win@4685afb
结论先行：
  • 纯启动：Zig 最快，几乎贴着 Windows 的进程创建“地板价”；Odin 次之（比地板高约 0.8 ms）；C3 最慢（比地板高约 1.7 ms）。差距全部来自 动态链接的 DLL 数量。
  • 完整提示符（会 spawn git status）：Odin 反而最快——因为它的 process_exec 不给子进程加 CREATE_NO_WINDOW，而 C3 / Zig 都会加，在本环境下每个被启动的进程要多花约 5–6 ms。
  • 这三者并不是“语言本身跑得快慢”的胜负，而是运行时与标准库默认行为的胜负：谁链接的 DLL 少、谁给子进程传的创建标志便宜，谁就赢。

no-op 基线的作用：它代表「在 Windows 上启动一个迷你 C 程序」的固定成本，用它减掉后剩下的才是各语言运行时的净开销。

2. 测量方法

因为要测的是 进程启动，量级只有几毫秒，任何测量器自身的开销都会污染结果，所以写了一个原生小 harness：

  • 用 CreateProcessW 启动子程序，WaitForSingleObject 等它退出；
  • 用 QueryPerformanceCounter 计整个「创建→退出」周期；
  • 子进程 stdout/stderr 重定向到 NUL，避免写控制台干扰计时；
  • 先 warmup 30 次，再采样 500 次，报告 min / p50 / mean / p95。

另有 4 个场景：--help（启动即退出）、非 git 目录（只算 cwd）、--short、以及 git 仓库内（会额外 spawn git status --porcelain）。

方法学陷阱：CREATE_NO_WINDOW 会凭空多花 ~6 ms。 最初用 CreateProcess(..., CREATE_NO_WINDOW) 写 harness，量出来基线就有 ~9 ms；换成 flags=0 后骤降到 ~2.9 ms（与 Python subprocess 互相印证）。四组对照（同一 no-op 子进程，p50）：
CreateProcess 调用p50 (ms)
CreateProcessA, flags=02.94
CreateProcessA, CREATE_NO_WINDOW9.13
CreateProcessA, NO_WINDOW + 句柄重定向9.22
CreateProcessW, flags=0 + 句柄重定向2.92
这个代价在本机可复现（连跑多轮稳定），但大概率与具体终端/会话环境有关，换机器建议自行复测。它恰好是第 4 节解释 Odin 为何反超的关键。

一个反直觉点：C3 的 MSVC 产物只有 110 KB（比 no-op 还小），却是启动最慢的；Zig 的 874 KB 反而最快。启动成本几乎与文件大小无关，取决于运行时要去 LoadLibrary 多少个 DLL。

为什么？—— 看导入表

用 objdump -p 抓每个可执行文件的依赖 DLL：

程序DLL 数依赖的 DLL
Zig2KERNEL32.dll, ntdll.dll
Odin3ADVAPI32.dll, bcrypt.dll, KERNEL32.dll
C3 (mingw)10UCRT 转发 DLL ×7 + dbghelp.dll + SHLWAPI.dll + KERNEL32.dll
C3 (msvc)11UCRT ×7 + VCRUNTIME140.dll + dbghelp.dll + SHLWAPI.dll + KERNEL32.dll

启动时间与 DLL 数量、尤其是重量级 DLL 高度相关：

  • Zig 只碰 KERNEL32 + ntdll，基本等于“地板”。
  • Odin 多拖两个：ADVAPI32（注册表/令牌）和 bcrypt（加密），代价约 +0.8 ms。
  • C3 走完整 UCRT（7 个 api-ms-win-crt-* 转发 DLL）外加 dbghelp.dll（用于调用栈/调试）——后者本身就会连带加载一批符号相关模块，是 +1.7 ms 的主要来源。

值得注意的是：C3 换 mingw 后端、开 -O3 -flto、体积从 110 KB 涨到 730 KB，启动却没变快——再次印证瓶颈是运行时 DLL 而非代码生成质量。

4. 完整提示符：当它会去 spawn git

真实使用时 bash_prompt 在 git 仓库里会执行 git status --porcelain。这一项由 git.exe 主导（单次约 25–30 ms），语言自身差异被稀释，但排序完全反转。

连跑三轮，Odin 领先约 5 ms 的结果稳定复现（28.3 / 29.4 / 29.3 vs Zig 33.0 / 32.7 / 33.5）。原因不在业务代码，而在三者启动子进程时传递的 dwCreationFlags：

// C3 · cmd.c3 —— 显式要求无窗口
Process process = process::spawn(
    command_line, STDERR_TO_STDOUT | INHERIT_ENV | NO_WINDOW)!;
//   SpawnOptions.NO_WINDOW  ⇒  CreateProcess 时设置 CREATE_NO_WINDOW

// Zig · std.process.run 的 RunOptions 默认值（lib/std/process.zig:495）
create_no_window: bool = true,      // 默认开！bash_prompt.zig 未覆盖它

// Odin · os.process_exec（core/os/process_windows.odin:512）—— 没有 NO_WINDOW
win32.CREATE_UNICODE_ENVIRONMENT | win32.NORMAL_PRIORITY_CLASS,
结合第 2 节的对照实验：CREATE_NO_WINDOW 在本环境下让每次进程创建多花约 6 ms。C3 显式打开、Zig 默认打开、Odin 不打开——这正好解释了 git 场景里那 ~5 ms 的差距。

可操作结论：在这个环境里，给 Zig 的 std.process.run 传 .create_no_window = false、给 C3 去掉 NO_WINDOW，就能把完整提示符追平甚至反超 Odin。也就是说，这里的胜负是一个可调参数，而非语言体质。

注意 C3 的 tmem/mem 与 Odin 的 context.allocator 都可以省略传递，所以出现次数少；Zig 必须逐个手动传 allocator，因此 allocator 出现 53 次、try/catch 出现 50 次——代码噪音主要来自这里。

5.2 入口与参数

// C3 —— 自定义入口，显式拿到 environ
fn int _main(int argc, ZString* argv, ZString* environ) @export("main")

// Odin —— 标准入口，参数从全局 os.args 取
main :: proc() {
    flag := parse_flags(os.args)
    ...
}

// Zig 0.17 —— 入口参数变成一个 Init 结构（io + arena + args + environ_map）
pub fn main(init: std.process.Init) u8 {
    return run(init) catch 1;
}

5.3 临时内存

// C3 —— 语言内置临时内存池，作用域结束自动回收
@pool() {
    Path target = cwd;
    for (;;) { Path git_dir = target.append(tmem, ".git")!; ... }
}
DString buf = dstring::new(tmem);

// Odin —— 用 context 里隐式携带的分配器
strings.builder_init_none(&out)
strings.write_string(&out, NEW_LINE)

// Zig —— 分配器必须一路显式传下去
var out: std.ArrayList(u8) = .empty;
try out.appendSlice(allocator, NEW_LINE);

5.4 运行子进程（差异最直接）

// C3 —— std 只给底层 spawn/read/join，仓库为此自写 cmd.c3（52 行）
Process process = process::spawn(command_line, STDERR_TO_STDOUT | INHERIT_ENV | NO_WINDOW)!;
defer (void)process.destroy();
close_stdin(&process);              // 手工关 stdin，否则子进程可能一直等输入
while (true) { char[8192] buf; sz len = process.read_stdout(&buf, buf.len) ?? -1; ... }

// Odin —— 一行拿到完整 stdout
_, stdout, stderr, err := os.process_exec(
    {command = argv[:]}, context.allocator,
)

// Zig —— 同样一行
const result = std.process.run(allocator, io, .{ .argv = argv.items }) catch return "";

C3 需要额外一个模块（cmd.c3）来补足标准库；Odin 与 Zig 都是开箱即用。

5.5 git 子命令的构造

// C3 —— 用 array::concat 拼接固定前缀
String[] final = array::concat(tmem,
    (String[]){"git","-C",self.root,"--no-optional-locks","--no-pager"}, command_line);

// Odin —— 动态数组 append
argv: [dynamic]string
append(&argv, "git", "-C", root, "--no-optional-locks", "--no-pager")

// Zig —— 同样是动态数组
var argv: std.ArrayList([]const u8) = .empty;
try argv.appendSlice(allocator, &.{ "git", "-C", root, "--no-optional-locks", "--no-pager" });

5.6 编译期技巧

// C3 —— macro，接近文本替换
macro String style(String $style, String $str) { return $style +++ $str +++ Ansi.RESET; }

// Odin —— 用 when 在编译期选常量
NEW_LINE :: "\r\n" when ODIN_OS == .Windows else "\n"

// Zig —— comptime 函数 + inline for + 字段反射
const NEW_LINE = textMode("\n");                 // 编译期把 \n 展开成 \r\n
inline for (flag_specs) |spec| {                 // 表驱动，比较在编译期展开
    if (std.mem.eql(u8, arg, spec.name)) @field(flag, spec.field) = true;
}

三者都能做到“零运行时开销的跨平台常量”，Zig 的 comptime 表达力最强但也最陡；C3 的 macro 最像宏；Odin 用 when 做条件编译最直观。

一句话总结：在同一台机器、同一份逻辑下，Zig 启动最快（≈ 进程创建地板）、Odin 完整提示符最快、C3 产物最小但启动最慢。三者差距都在“几毫秒”量级，且都能通过减少依赖 DLL 或 调整子进程创建标志来抹平——真正决定性能的是运行时/标准库的默认选择，而不是语言语法。

选型建议

  • 把 bash_prompt 这种每次回车都要跑一遍的工具当目标时，启动延迟最值钱：优先选 Zig（启动最快），并确认子进程创建标志是否可关掉 CREATE_NO_WINDOW。
  • 如果工作负载本身就重（要频繁跑 git 等外部命令），Odin 在这里的整体表现最好，代码也最短。
  • C3 的强项是体积与高层标准库（路径/JSON/字符串），但对“启动敏感”的 CLI，需要注意它默认会链上 UCRT 与 dbghelp；若要紧，考虑裁剪调试符号支持。
  • 三者都能编译成零 GC 原生程序，用任意一个做这类工具都完全合格——差异是工程权衡，不是可行性问题。
